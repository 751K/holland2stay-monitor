# 平台侦察与历史评估

本文将平台资料分为两部分：已接入平台的实现与历史观察，以及尚未接入平台的历史
侦察记录。本文依据当前仓库中的平台注册表和既有侦察资料整理；本次整理没有重新访问
第三方站点，也没有复核其接口、房源数量、服务条款或反爬措施。

**历史观察只反映相应探测时间的样本，不能作为当前站点状态或接入承诺。** 旧文档对
平台的排序、工作量和接入价值作过估计；这些估计没有经过本次复核，本文不再将它们
列为当前决策。平台的服务条款、robots.txt、数据使用权限和分配规则需要分别核查；
robots.txt 的内容不能单独证明数据使用或再分发获得许可。

当前平台登记与调度机制见 [架构总览](ARCHITECTURE.md#平台与抓取)，后续产品工作见
[FUTURE_PLAN.md](FUTURE_PLAN.md)。本文重写前的详细历史记录可通过 Git 查看：
`git show 1dbc0f9:docs/SCRAPING_RECON.md`。代码说明反映项目当前实现，平台响应则
需要重新验证。

## 1. 已接入平台：实现与历史观察

当前仓库在 [mcore/sources.py](../mcore/sources.py) 中登记了 Holland2Stay、OurDomain、
OurCampus、Xior、Magis、Student Experience 和 Plaza。登记表示项目具备相应抓取器，
不代表某个部署已启用该平台，也不保证上游接口当前可用。Holland2Stay、Xior 和
OurDomain 分别见 [H2S.md](H2S.md)、[XIOR.md](XIOR.md) 和 [OURDOMAIN.md](OURDOMAIN.md)；
三者共用的 RENTCafe 预订流程见 [RENTCAFE.md](RENTCAFE.md)，Plaza 自动应征见
[PLAZA.md](PLAZA.md)。

| 平台 | 当前仓库入口 | 本节历史观察的时间 |
|---|---|---|
| Magis | [scrapers/magis.py](../scrapers/magis.py) | 2026-09-01 |
| OurCampus | [scrapers/ourcampus.py](../scrapers/ourcampus.py) | 2026-08 至 2026-09 |
| Student Experience | [scrapers/studentexperience.py](../scrapers/studentexperience.py) | 2026-09-01 至 2026-09-02 |

### 1.1 Magis

项目通过 HTTP 请求 `/for-rent?only_available=0`，并在同一批次内复用页面内容，按照
配置的城市划分抓取结果。抓取器从服务端渲染的房源卡片中解析单元、状态、租金和
其他属性。当前租金处理使用卡片中识别到的基础租金和服务费；用户仍需核对平台的
实际报价。实现见 [scrapers/magis.py](../scrapers/magis.py)。

2026-09-01 的探测记录包含五个城市、17 栋楼和 12 条房源样本，其中四条处于可租状态。
当时的样本显示，`only_available=0` 可返回部分不可租单元，卡片中的服务费能够用于
计算合计金额；这些数量和字段可用性均不能视为当前事实。

解析器应根据字段模式而不是固定文本行号识别房源信息，因为历史样本中的设施或租客
标记会改变文本位置。项目没有将 Magis 的租客要求登记为可过滤维度：历史样本未能
证明没有学生徽标的房源一定不受资格限制。Magis 未开放自动预订；用户仍需核实
具体房源的资格与费用。

### 1.2 OurCampus

OurCampus 抓取器继承 OurDomain 的 RENTCafe 解析器，并覆盖单元表请求方式：
OurCampus 使用包含 `floorPlans[]` 的 POST 请求。代码复用指纹处理、状态解析及完整性
判断；具体实现见 [scrapers/ourcampus.py](../scrapers/ourcampus.py) 和
[scrapers/ourdomain.py](../scrapers/ourdomain.py)。

2026 年的样本用于纠正两项状态判据：页面可能同时包含可订和不可订单元；按钮文字
`Book Now` 与 `Join Lottery` 对应不同状态。抓取器应结合按钮存在情况和文字判断，
不能仅凭按钮存在就断定房源可直接预订。

对于空结果，抓取器检查响应是否具有预期单元面板结构，并要求连续多轮确认；默认
确认次数为三轮。结构发生变化但页面仍满足面板探针时，这些检查也可能无法识别解析
失配，维护者需要结合采集记录和平台页面核对。项目未开放 OurCampus 自动预订。

### 1.3 Student Experience

项目以**户型**而非具体房间为房源粒度。抓取器分别读取长租页面和短租学期档，并在
一个批次内复用结果；短租抓取会遍历各楼盘返回的学期档。历史样本表明，同一户型可能
只出现在部分学期档中，因此单一档期的结果不能证明该户型在其他档期不可用。

当前实现使用长租页面的楼盘计数块作为结构与数量校验依据。计数块缺失，或解析出的
长租卡片数量少于计数时，抓取器将扫描标记为不完整；短租档期解析失败也会影响完整性。
这些检查降低了把解析失败当成空房源的风险，但不能保证识别所有上游结构变化。实现
见 [scrapers/studentexperience.py](../scrapers/studentexperience.py)。

历史卡片以 `From` 表示户型起价，面积也可能是区间，不能将其视为某一房间的确定租金
或面积。当前过滤能力登记了户型和租客维度，但没有登记装修、楼层和能耗维度；具体
能力以 [mcore/sources.py](../mcore/sources.py) 为准。2026 年的侦察还记录了部分短租
房源可能具有居住地、国籍或其他资格要求；用户应在申请前核实平台当前规则。项目未
开放该平台自动预订。

### 1.4 Plaza

当前抓取器向 `/portal/object/frontend/getallobjects/format/json` 发送 POST 请求，
在批次内共享响应，并筛选荷兰住宅。抓取器根据每条房源的字段记录分配方式和租客
要求；系统不能假定同一平台的所有房源采用相同的分配机制。实现见
[scrapers/plaza.py](../scrapers/plaza.py)。

抓取器要求响应中的 `result` 为列表，并检查 `sAngularServiceData` 中的门户配置
探针。响应不符合预期时，抓取器将结果标记为不完整；接口返回非 JSON 内容时，抓取器
报告网络或响应错误。平台新增城市或调整字段后，维护者还需要检查配置和日志。

2026-09-02 的历史样本包含 49 条荷兰住宅，其中出现 `dth` 和 `reactiedatum` 两种
分配模型。站点当时还定义了抽签、按注册时长排序等模型，样本中未出现这些模型并不
代表其将来不会出现。2026-09-10 的资格测试还发现，部分额外供给房源仅面向特定
受邀用户；开放日期或一般的登录状态不能单独证明某个用户有应征资格。

当前判据是 `isExtraAanbod`：为真表示该房源属于额外供给，只对受邀账号开放，抓取器
按不可应征处理。**不要用 `closingDate` 判断是否在架**（实测恒等于 `publicationDate`
加一年），也不要把分配模型（`dth`）当作可用性——DTH 只是分配方式。判据与反例说明
见 `scrapers/plaza.py` 的 `_EXTRA_AANBOD_NOTE`，测试在
`tests/test_plaza_scraper.py::TestExtraAanbod`。

Plaza 支持用户单独启用自动应征；结果不确定时，系统按账号和房源保留保护。应征
不保证获得房源，且用户需要核实房源资格和平台当前费用。自动应征的验证范围、限制
与未解决问题见 [PLAZA.md](PLAZA.md)。

### 2.1 HousingAnywhere：页面数据与分页

2026-08-03 的记录在搜索页面中观察到 `window.__staticRouterHydrationData`，其中
包含列表数据。原记录称数据需要处理 JavaScript 字符串与 JSON 两层编码，并指出
旧的 JSON-LD 和 `__PRELOADED_STATE__` 路径在当次样本中不再包含单条房源。站点页面
结构可能已经改变，实施时应重新确认数据来源和解析方式。

原记录同时指出，站点当时的 robots 规则对 API 路径和带查询参数的搜索路径存在不同
限制，分页是否适用相关规则尚有疑问。未来评估需要同时核对当前规则、服务条款和
实际使用权限；仅抓取第一页也不能证明数据使用获得授权。评估还需要说明不翻页时
列表覆盖范围和完整性如何表达，不能将第一页缺失视为全量房源消失。

### 2.2 SSHXL 与 SSH&：区分平台和资格条件

2026-09-01 的 SSHXL 侦察记录了 `/api/v1/offering/filters` 和
`/api/v1/offering/all` 两个短租接口。原记录指出，查询参数依赖院校配额、学生类型和
租期，所测组合没有返回房源；因此，当时尚无真实房源样本可用于验证字段和状态映射。
原记录还称长租使用不同的注册和排队流程，该判断需要在重新评估时核实。

SSH& 是另一家机构。原记录描述其门户使用 Embrace GraphQL 和 Keycloak 登录，并将
会员资格与分配方式列为接入限制；原文没有完整记录探测日期。未来评估应分别核对两家
机构的公开数据、账号条件及使用权限，不应根据名称相似推断接口或规则相同。

### 2.3 DUWO / ROOM 与 Vesteda：数据访问和分配方式

原记录对 DUWO / ROOM 的判断基于当时观察到的匿名搜索响应、注册要求和条款；原文未
明确记录该次探测日期。用户是否能够查看房源、服务是否允许数据再利用、以及房源如何
分配，属于三个独立问题，需要分别复核。收费本身不能证明公开数据不可访问，也不能
单独决定平台是否适合接入。

2026-09-01 的 Vesteda 探测记录了 `POST /api/units/search/facet`，当时返回结构化
房源数据。原记录称站点依据资格等条件评分，并在同分时采用抽签；当时因此没有推进
接入。未来评估应核对当前分配规则及用户需求，不能把“是否先到先得”作为判断通知
价值的唯一标准。

### 2.4 Gapph / Ad Hoc：房源粒度与合同性质

2026-09-01 的记录描述了 Gapph 的服务端页面和 Ad Hoc 的 WordPress 数据接口。原文
称部分页面的一条记录可能涵盖多个户型，价格和面积也可能位于正文；这会影响房源
粒度、字段提取及过滤可靠性。站点是否仍采用相同结构需要重新确认。

原记录还区分了 `antikraak`（空置看护或借用安排）与 `tijdelijk-huren`（临时出租）
两类房源。未来若考虑接入，产品设计应先明确合同类别、费用和限制如何向用户展示，
并核实当前合同条款；不能根据单一历史样本概括所有房源的法律性质或权利义务。

## 3. 重新评估时的检查范围

在决定接入任何候选平台之前，维护者应重新核对以下内容，并记录探测时间、样本范围
和未验证事项：

1. **数据范围与权限。** 确认匿名与登录后的可见范围、服务条款、robots 规则和数据
   使用权限，并区分抓取、存储、展示、通知及自动操作等用途。
2. **数据与完整性。** 确认城市、房源粒度、分页、状态、价格口径和空结果判据。系统
   应将未知或不完整结果标记为不完整，避免使用这些结果推断房源下架。
3. **用户资格与分配。** 确认注册、费用、租客资格、合同性质和分配规则。维护者应
   区分历史观察、平台当前规则和项目自身的产品决策。
4. **传输与维护成本。** 核对访问限制、限流、代理、浏览器资源和上游变更风险；
   历史一次请求成功不能证明长期可用。
5. **自动操作。** 抓取能力不等于自动预订或应征能力。任何自动操作都需要单独评估
   授权、真实流程、结果不确定保护和通知方式。

未接入平台的进一步工作属于候选研究，不构成发布承诺；当前计划以
[FUTURE_PLAN.md](FUTURE_PLAN.md) 为准。
